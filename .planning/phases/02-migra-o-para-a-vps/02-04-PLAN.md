  <how-to-verify>
    1. **Bucket.** Criar um bucket **privado** no provedor S3-compatível escolhido (Backblaze
       B2 é a suposição A5 da pesquisa; qualquer equivalente serve). Criar uma chave de
       aplicação **limitada a esse bucket**, não uma chave de conta. Anotar `bucket`,
       `endpoint` e `region`.
    2. **Chave de deploy.** Numa máquina confiável:
       `ssh-keygen -t ed25519 -C "dg2-deploy@github-actions" -f ./dg2-deploy -N ""`.
       Instalar `dg2-deploy.pub` em `~dg2-deploy/.ssh/authorized_keys` na VPS, com o prefixo
       de restrição na mesma linha:
       `command="/srv/dg2/bin/deploy-forced.sh",no-port-forwarding,no-agent-forwarding,no-pty,no-user-rc `
       antes do `ssh-ed25519 ...` (o script vem do plano 02-03 e é instalado no plano 02-12;
       a linha pode ser escrita agora).
    3. **Chave de host.** `ssh-keyscan -t ed25519 <host>` executado **uma vez**, de máquina
       confiável, e conferido contra o fingerprint mostrado no console do provedor. A saída
       é o valor de `DEPLOY_KNOWN_HOSTS`. **Nunca** rodar `ssh-keyscan` dentro do job de CI:
       é confiar no primeiro que responder, dentro do único pipeline que carrega a chave.
    4. **Secrets.** `gh secret set DEPLOY_SSH_KEY < ./dg2-deploy`,
       `gh secret set DEPLOY_HOST`, `gh secret set DEPLOY_USER` (valor `dg2-deploy`),
       `gh secret set DEPLOY_KNOWN_HOSTS`. Conferir com `gh secret list` que os quatro
       existem. Apagar a cópia local da chave privada depois de gravar o secret.
    5. Confirmar que **nenhum** desses valores foi escrito em arquivo do repositório.
       `git status --porcelain` não deve mostrar nada além do que a Task 3 cria.
  </how-to-verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| runner do GitHub → VPS | uma chave privada guardada num serviço de terceiro tem escrita na caixa |
| VPS → bucket S3 | credencial de longa duração vive em `/etc/dg2/env` e replica o banco continuamente |
| repositório → internet | tudo o que for escrito em `docs/` fica legível se o repositório for público |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-SSH | Spoofing / Tampering | captura da chave de host | mitigate | `ssh-keyscan` executado **uma vez**, de máquina confiável, conferido contra o fingerprint do painel do provedor, e o valor fixado no secret `DEPLOY_KNOWN_HOSTS`. Nunca dentro do job de CI: seria confiança no primeiro que responder, dentro do único pipeline que carrega a chave privada |
| T-2-KEY | Elevation of Privilege | `dg2-deploy` na VPS | mitigate | Chave `ed25519` dedicada, instalada com `command="/srv/dg2/bin/deploy-forced.sh",no-port-forwarding,no-agent-forwarding,no-pty,no-user-rc`; a cópia local da privada é apagada depois de virar secret |
| T-2-BUCKET | Elevation of Privilege | credencial do bucket | mitigate | Chave de **aplicação limitada ao bucket**, não chave de conta. Bucket privado. Um comprometimento da VPS não vira acesso ao resto do armazenamento |
| T-2-SECRET | Information Disclosure | `docs/OPERACAO.md` | mitigate | O documento registra plano, região e **nomes** de chave; nunca IP, domínio ou valor. Asserido por teste (nenhum IPv4 além de `127.0.0.1`, nenhum `AWS_SECRET_ACCESS_KEY=` com valor) |
| T-2-SC | Tampering | — | accept | Nenhum pacote instalado neste plano; `gh` e `ssh-keygen` são binários já presentes na máquina |
</threat_model>
